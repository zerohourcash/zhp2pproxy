# Official publication and release checklist

## One-time repository settings

- Enable two-factor authentication for maintainers.
- Protect the default branch and require the `CI` check.
- Require pull-request review and block force pushes/deletion.
- Enable private vulnerability reporting and secret scanning.
- Limit release/signing secrets to a protected release environment.
- Keep the Ed25519 private key and Authenticode private key outside Git.

## Source publication

1. Run `./scripts/ci.sh` and review `git diff --check`.
2. Confirm `gitleaks git --redact --no-banner` reports no findings across all
   history.
3. Confirm `git status --ignored` shows runtime configs and identities ignored.
4. Review the complete diff and commit it.
5. Create a signed annotated version tag on the exact reviewed commit.

Do not upload a zip of a live installation directory. Publish Git source or a
source archive generated by the hosting platform from the tagged commit.

## Binary release

The release command requires:

- a clean worktree at an exact Git tag;
- `UPDATE_SIGNING_KEY` pointing to the offline Ed25519 private key;
- a 14..18 digit monotonic `BUILD_SEQUENCE`; the default UTC
  `YYYYMMDDhhmmss` value should normally be used so a release cannot sort below
  older timestamp-based builds;
- for a Windows release, `WINDOWS_SIGN_COMMAND` signing one EXE path with
  Authenticode and `WINDOWS_VERIFY_COMMAND` independently validating it;
- `PUBLISH_DIR` set to a staging directory, never directly to a live web root.

Update URLs are fixed to GitHub Releases under
`https://github.com/zerohourcash/zhp2pproxy`. Mirrors may distribute files for
manual recovery, but the automatic updater deliberately rejects them.

Example shape (signer-specific commands are intentionally not stored here):

```bash
UPDATE_SIGNING_KEY=/secure/offline/update-ed25519.pem \
WINDOWS_SIGN_COMMAND=/secure/bin/sign-windows \
WINDOWS_VERIFY_COMMAND=/secure/bin/verify-windows-signature \
PUBLISH_DIR=/secure/release-staging/vX.Y.Z \
./release.sh
```

When a trusted Authenticode certificate is unavailable, the default remains a
Linux-only release. An operator may publish visible, manual-update Windows
binaries only after an explicit product decision:

```bash
UPDATE_SIGNING_KEY=/secure/offline/update-ed25519.pem \
RELEASE_WINDOWS=1 \
ALLOW_UNSIGNED_WINDOWS_RELEASE=1 \
PUBLISH_DIR=/secure/release-staging/vX.Y.Z \
./release.sh
```

Unsigned Windows builds remain notification-only and must be identified as
such in release notes. The public staging directory intentionally contains only
Windows EXE files, Linux executable binaries, and the signed `update.json` plus
`update.json.sig`. Documentation, SBOM, checksums and license bundles stay in
Git source or internal build output instead of cluttering GitHub release assets.

Review internal `SHA256SUMS`, verify `SHA256SUMS.sig` with
`release/update-public.pem`, inspect `SOURCE_COMMIT` and the SBOM, then verify
that the public staging directory contains only the expected executables and
the signed update manifest pair. Never publish from a dirty worktree.

## Rollout

Roll out to one non-critical relay first. Verify `/health`, a local RPC call, a
P2P fallback call, browser RPC and native node handshake. Then expand gradually
while monitoring errors and peer connectivity. Keep the previous signed release
available for rollback.
